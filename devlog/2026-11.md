## 2026-11-02 -- Bound Windows service stop verification

## 2026-11-02 -- Windows service stop now ends the Node process, not only the launcher

With the script host launcher, the scheduled task's process is `wscript.exe`
and Node is its child. A probe on the hosted Windows runner showed that
`taskkill /PID <wscript> /F` leaves Node running, and that registering the real
task definition, running it and ending it with `schtasks /End` also left Node
alive. Left alone, `arco service stop` would not stop Arco, a restart would hit
the held port, and `arco update` would refuse because Arco processes were still
running. `serviceAction('stop')` in `scripts/packaging/services.mjs`, which
`restart` and `uninstall` also use, now ends the task and then runs a short
PowerShell step that selects `wscript.exe` and `node.exe` processes whose
command line contains this home's `service/config.json` and ends each with
`taskkill /T /F`. The marker is the per-home configuration path, so another
home's Arco and a source-checkout service are not matched. The update guard is
unchanged and stays the final check. A unit test covers the order and the
failure path. `scripts/packaging/pack-smoke.mjs` starts a stand-in service
through the written launcher, kills only the launcher as `/End` does, runs the
real stop code, and requires both processes gone and the port free. Checked on
Linux with the unit suite and gate; the Windows result comes from the hosted
pull request run. Not verified: a real Windows desktop.

## 2026-11-02 -- Windows service runs without a console window

The Windows logon task `arco-workbench` ran `node.exe` directly (`<Exec><Command>` in `scripts/packaging/services.mjs`), so a console window stayed open on the desktop streaming the server log and git warnings. `renderService('win32')` now registers `C:\Windows\System32\conhost.exe --headless <node> <arco.mjs> service-run <config>` (path from `SystemRoot`, every argument quoted).
