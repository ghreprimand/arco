When Arco restarts, it reaps worker processes left over from the previous run. `reapProc` (`server/src/workers/pidRegistry.ts`) kills a recorded pid only when its start time matches the recorded one, so a pid the system has since reused for an unrelated process is left alone. `readStartTime` in `server/src/workers/processStartTime.ts` read `/proc` on Linux and `ps` on macOS, and returned nothing on Windows. Without a start time the reaper fails toward killing, so on Windows a reused pid could be killed. On the hosted Windows runner, `pidReuse.test.ts` showed exactly that: the test that records a wrong start time for its own pid killed its own process.

On Windows the start time now comes from `powershell.exe -NoProfile -NonInteractive`, as `[System.Diagnostics.Process]::GetProcessById(<pid>).StartTime.ToFileTimeUtc()`. That value is stable for the life of the process. The call runs hidden with a 15-second timeout, and an error still returns null. A first version used `Get-Process` with a five-second timeout; on the hosted runner its cold module autoload exceeded the timeout, so the start time was never read. The .NET call skips that autoload. The recycled-pid test is skipped on any platform where the test's own start time cannot be read, so a missing reader fails one assertion instead of killing the test file. The stable-token test now covers Windows as well.

Checked: `pidReuse.test.ts` 8/8 and `npm run test:unit` 802/802 on Linux. The Windows reader is checked by the hosted run dispatched on this branch.

Open: PowerShell startup adds a few hundred milliseconds per reaped pid on Windows; reaping happens once at startup.

## 2026-10-25 -- Atomic writes retry a blocked rename on Windows

Every settings, workflow and registry store writes through `atomicWriteFile` and `atomicWriteFileSync` in `server/src/atomicFile.ts`. ## 2026-10-25 -- Provider CLIs installed through npm start on Windows

On Windows, npm installs `codex`, `claude`, `gemini`, `cursor-agent`, `npx` and most language servers as `.cmd` shims. Node refuses to spawn a `.cmd` or `.bat` file without a shell, so every provider turn, sign-in check, catalog probe and capability check failed on a native Windows run, as did MCP servers configured as `npx ...` and npm-installed language servers. Running the shims through `cmd.exe` would reopen the argument-quoting hole that made Node add the restriction.

The new `server/src/windowsCommand.ts` resolves a command the way `cmd.exe` would, through `PATH` (any case, quoted entries allowed) and `PATHEXT`. A native `.exe` or `.com` is started by its full path. For a `.cmd` or `.bat` it reads the shim, takes the script path npm's cmd-shim writes after `%dp0%` (or the older `%~dp0`), and starts that `.js`, `.mjs` or `.cjs` file with the running Node binary, keeping every argument as a separate argv entry. Anything it cannot resolve passes through unchanged; on Linux and macOS it does nothing. 25 call sites use it through `commandArgs()`: the Claude, Codex (exec and app-server), Cursor and Gemini workers and catalogs, the toolbox and context calibrator probes, voice Luna and input observation, `auth.ts`, `capabilities.ts`, the diagnostics version check, the MCP client and the LSP client. `docs/OPERATIONS.md` describes this in the Windows note.
