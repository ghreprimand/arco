## 2026-10-25 -- @file references work in projects reached through a symlink

On the hosted `macos-latest` runner four `server/src/contextRefs.test.ts` cases failed with zero expanded references. The `@file:` expansion in `server/src/contextRefs.ts` resolves the target's realpath to stop a symlink escaping the project, then compared it with the project path as given. When the project path itself goes through a symlink, as every macOS temporary folder does (`/var` is a link to `/private/var`), every file looked outside the project and was refused as a symlink escape. The same happened on Linux for a project opened through a symlinked folder. The comparison now uses the project's realpath, falling back to the resolved path if it cannot be read.

Checked: a new test opens a project through a symlinked folder and expands `@file:a.txt`; it failed before the fix with zero expansions and passes after it. A second new test confirms that a link inside the project pointing at a file outside it is still refused with the symlink-escape notice. `contextRefs.test.ts` passes 9/9 and `npm run test:unit` passes 793/793 on Linux. `writeConfinement.ts` and `fileAccessPolicy.ts` already compare realpaths on both sides. The explorer home fence (`realpathWithinHome` in `explorerArtifacts.ts`) compares a realpath with the unresolved home folder, so a symlinked home would hide every project from it; no test fails on it, so it is recorded on the board rather than changed here.

Open: confirmation on macOS comes from the next hosted CI run.
